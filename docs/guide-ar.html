flutter-agent

وكيل محلّي لمعمارية Flutter النظيفة. بحث دلالي داخل كود Dart الخاص بك، وتطبيق صارم لقواعد الطبقات، وتوليد الـ features بأسلوب مشاريعك، ومخزن دروس يتعلّم من جلسات Claude.

يعمل بالكامل على جهازك. لا يخرج أي سطر من الكود إلى الإنترنت، والـ embeddings تُحسب على كرت الشاشة لديك.

المحتوى المفهرس: 896 ملفًا · 1,664 مقطعًا من corereusablepackage وbilhikma وhikmaapp وskygate وattendence.

واجهتان: أدوات MCP داخل Claude Code، وسطر الأوامر flutter-agent.

1. ما هو ولماذا وُجد

أعرافك في كتابة Flutter موجودة في مكانين لا يتحدث أحدهما إلى الآخر: ملف نصّي يشرحها، وقرابة 900 ملف Dart لا يستطيع شيء البحث فيها.

كل جلسة جديدة مع Claude Code تعيد استنتاج معماريتك من CLAUDE.md — أي من وصف القواعد، لا من الكود الذي يطبّقها فعلًا. وكل تصحيح تكتبه يضيع بانتهاء الجلسة.

هذا الوكيل يسدّ الفجوتين:

  • يفهرس كودك الحقيقي. حين تسأل «كيف نعمل pagination؟» يجيبك بـ PaginatedResult الخاص بك، لا بمثال عام من الإنترنت.
  • يطبّق قواعدك تطبيقًا ثابتًا. اثنتا عشرة قاعدة تقرأ الكود وتحكم عليه — بلا أي نموذج ذكاء اصطناعي، فهي سريعة ومجانية ونتيجتها واحدة في كل مرة.
  • يولّد الكود بأسلوبك. أي feature يولّده مبنيّ على bilhikma/features/archive، وهو أنظف تطبيق للمعمارية في مشاريعك.
  • يتذكّر التصحيحات. حين تصحّح لـ Claude خطأ، يُسجَّل التصحيح ويُفهرس ويعود للظهور في الجلسات القادمة.

ما ليس هو

ليس مولّد كود يغنيك عن التفكير، ولا يقرّر إن كان الكود يُصرَّف (compile) أم لا — فـ flutter analyze يبقى المرجع الوحيد في ذلك، والوكيل يستدعيه فعليًا بدل أن يحاكيه.

المعمارية التي يفرضها

كل feature مكوّن من نصفين فقط، ولا وجود لـ domain/ أو entities/ أو use_cases/ أو repo_interface/:

lib/features/<feature>/
  data/
    data_source/   # the ONLY place that talks to a backend or storage
    models/        # fromJson / toJson
    repos/         # delegation only, no logic
  presentation/
    cubit/         # every decision the screen makes
    refactor/      # body sections pulled out of a screen
    screens/       # 30-70 lines: create the cubit, render the body
    widgets/       # small dumb components

2. كيف يعمل

Dart projects ───────┐
knowledge/           ├─► parser ─► chunker ─► embeddings (GPU) ─► FAISS ─┬─► MCP ─► Claude Code
 (rules, patterns,   │                                                  └─► CLI
  lessons)  ─────────┘

الخطوات

  1. التحليل (parse). ماسح Dart مكتوب يدويًا يستخرج التعريفات والأعضاء والـ imports والنصوص. ليس مُصرِّفًا ولا يحاول أن يكون — مهمته تحديد الحدود والبيانات الوصفية.
  2. التقطيع (chunk). مقطع لكل تعريف رئيسي. الـ Cubit الذي يبلغ 600 سطر يُقسَّم عند حدود الدوال، وكل جزء يحتفظ بترويسة الـ class حتى يبقى المقطع مفهومًا بذاته.
  3. الوسم (tag). كل مقطع يحمل اسم المشروع والـ feature والطبقة والرمز ونطاق الأسطر. هذا ما يجعل --layer data_source ممكنًا.
  4. التمثيل (embed). يُحسب محليًا على كرت RTX 4050 بنموذج all-MiniLM-L6-v2 (نحو 90 ميغابايت). فهرسة كل الكود تستغرق نحو 24 ثانية.
  5. التخزين. FAISS للمتجهات وSQLite للبيانات الوصفية، مربوطين بحيث لا يمكن أن يختلفا.
  6. التقديم. عبر MCP إلى Claude Code، وعبر سطر الأوامر إليك.

الفهرسة تراكمية. لا يُعاد حساب إلا الملفات التي تغيّر محتواها (بمقارنة SHA-256). إعادة الفهرسة بعد تعديل cubit واحد تكلّف عملية واحدة لا تسعمائة — عادةً أقل من ثانيتين.

لماذا التحليل اللغوي مهم

عدّ الأقواس في النص الخام ينهار فور ظهور قوس داخل تعليق أو نص أو داخل ${...}. لذلك يعمل كل شيء على نسخة مُقنَّعة من الملف، تُمحى فيها التعليقات والنصوص حرفًا بحرف مع الحفاظ على المواضع. هذا يتعامل بشكل صحيح مع التعليقات المتداخلة، والنصوص الخام والثلاثية، وحالة '${map['key']}' الصحيحة لغويًا والمربكة.

كذلك لا تُعدّ الأقواس المعقوفة إلا خارج الأقواس الهلالية، لأن Dart يكتب الوسائط المسمّاة هكذا: ({required this.repo}) — واعتبارها بداية جسم يقطع كل constructor من هذا النوع إلى نصفين.

مُختبَر على كودك: 885 ملفًا، 1,332 تعريفًا، 8,137 عضوًا، بدون أي انهيار.

5. استخدامه داخل Claude Code

هذه الطريقة الأساسية. أنت لا تستدعي الأدوات بنفسك — تطلب طلبك بلغة عادية، وClaude هو من يستدعيها.

ما تقولهما يفعله Claude
«أضف feature للإشعارات في bilhikma»flutter_pattern ثم flutter_component ثم flutter_scaffold
«راجع ما كتبته في features/profile»flutter_check على المجلد
«ملف الـ body هذا طويل، قسّمه»flutter_refactor_plan ثم ينفّذ التقسيم
«كيف نتعامل مع الأخطاء هنا؟»flutter_pattern("error handling")
«هل يوجد widget للحالة الفارغة؟»flutter_component()

ويمكنك تسمية الأداة صراحةً: «استخدم flutter_search لتجد كيف نعمل pagination».

الأدوات العشر

الأداةما تجيب عنه
flutter_patternكيف يفعل هذا الكود كذا — القاعدة ومثال نموذجي والتصحيحات السابقة. استدعها قبل التنفيذ.
flutter_searchبحث دلالي في كود Dart مع تصفية حسب الطبقة أو الـ feature أو المشروع أو النوع
flutter_componentما تصدّره الحزمة المشتركة، ومع اسم: تعريف المكوّن ومواضع استخدامه الحقيقية
flutter_checkمخالفات قواعد المعمارية في ملف أو feature أو مشروع
flutter_refactor_planما الذي يُستخرج من ملف متضخّم، مرتّبًا من الأكبر، مع سابقة نظيفة يُحتذى بها
flutter_scaffoldمجلد feature كامل مع مفاتيح الترجمة. تجربة بلا كتابة افتراضيًا
flutter_lesson_addتسجيل تصحيح ليُستدعى لاحقًا
flutter_lessonsاسترجاع التصحيحات حسب الموضوع
flutter_reindexإعادة مسح المصادر بعد تعديلات كثيرة
flutter_statusحالة الفهرس والمصادر والجهاز والأعداد

لماذا يجعل هذا Claude أرخص كما يجعله أدق. بلا الوكيل، الإجابة عن «كيف نعمل pagination هنا» تعني قراءة عدة ملفات Dart كبيرة كاملة. أما flutter_pattern فيعيد بضع مئات من الـ tokens تحتوي التعريفات ذات الصلة فقط.

الخطوة 4 — ما يتبقّى عليك

الـ data source يأتي بهيكل عامل مع عقد الأخطاء جاهزًا. استبدل جسم fetchItems بالاستدعاء الحقيقي:

Future<List<NotificationsModel>> fetchItems() async {
  try {
    // replace this with the real backend call
    const List<Map<String, dynamic>> raw = <Map<String, dynamic>>[];
    return raw.map(NotificationsModel.fromJson).toList(growable: false);
  } on NotificationsException {
    rethrow;
  } catch (error) {
    throw NotificationsException(mapError(error));
  }
}

ثم سجّله في الـ service locator، ولاحظ registerFactory للـ cubit:

getIt
  ..registerFactory(() => NotificationsCubit(repo: getIt()))
  ..registerLazySingleton(() => NotificationsRepo(dataSource: getIt()))
  ..registerLazySingleton(NotificationsDataSource.new);

الـ cubits تُسجَّل دائمًا بـ registerFactory. تسجيل cubit كـ singleton يبقي حالة الشاشة السابقة ويُطلق emit بعد close() — وهو أشهر سبب لمشكلة «الحالة من آخر مرة فتحت فيها هذه الشاشة».

8. قواعد المعمارية

اثنتا عشرة قاعدة ثابتة. لا نموذج ذكاء اصطناعي في أيٍّ منها — كل قاعدة خاصية في الكود يمكن الحكم عليها بالقراءة.

كل المطابقات تجري على النسخة المُقنَّعة من الملف، لذا يستحيل أن تنطلق قاعدة بسبب كلمة داخل تعليق أو نص.

الـ cubit له حدّ واسع لأن السلوك وظيفته فعلًا. أما الشاشة فحدّها ضيّق لأن الشاشة التي تجاوزته تكون قد ابتلعت عملًا يخصّ cubit أو widget.

القاعدة R6 عمليًا — أهم قاعدة

// WRONG - the cubit reaches into the widget tree
Future<void> save() async {
  await repo.save();
  Navigator.of(context).pop();
  ScaffoldMessenger.of(context).showSnackBar(...);
}

// RIGHT - the cubit emits, the screen listens
Future<void> save() async {
  await repo.save();
  if (isClosed) return;
  emit(state.copyWith(status: ProfileStatus.saved));
}

الـ cubit يعيش أطول من أي widget وقد يُصدر حالة بعد اختفائه. الاحتفاظ بـ context ينتج عنه في أحسن الأحوال خطأ «استخدام BuildContext عبر فجوة غير متزامنة»، وفي أسوئها انهيار التطبيق.

if (isClosed) return; بعد كل await وقبل كل emit. المستخدم قد يغادر الشاشة أثناء الطلب، والإصدار على cubit مغلق يرمي استثناءً. هذا السطر موجود في كل cubit في كودك — ليس أسلوبًا اختياريًا.

القاعدة R7 عمليًا

Text('saved_items'.tr())   // raw key - nothing stops a typo
Text('Saved items')       // hardcoded, never translated
Text(LangKeys.savedItems.tr())

الثابت ليس زينة: 'saved_itmes'.tr() يُصرَّف ويُنشر ويعرض المفتاح نفسه للمستخدم، بينما LangKeys.savedItmes لا يُصرَّف أصلًا.

والنصوص المُدمَجة وغير اللغوية تُستثنى بشكل صحيح: Text('$count') وText('-') وText('2x').

الموجود حاليًا

بطاقات قواعد: layering، localization، errors، file-size.
بطاقات أنماط: cubit-and-state، screen-and-body، data-source-and-model، pagination، dependency-injection.

هذا هو الجزء الذي تنمّيه أنت. أي موضوع بلا بطاقة ستكون نتيجته أضعف. وأسرع طريقة لإضافة بطاقة أن تطلب من Claude: «اكتب بطاقة نمط لرفع الصور بناءً على طريقة skygate» — فيقرأ الكود ويكتب الملف، ثم تعيد الفهرسة.

كيف تكتب بطاقة جيدة

  • اعرض كودًا حقيقيًا من مشاريعك، لا أمثلة مخترعة.
  • اشرح القرار لا الصياغة. «لماذا وُجد clearError» مفيد، أما «copyWith ينسخ الحالة» فلا.
  • أدرج النسخة الخاطئة. البحث يصبح أدق كثيرًا في التقاط خطأ على وشك الحدوث حين يكون الخطأ مكتوبًا.
  • موضوع واحد لكل ملف بعناوين ## — فالمقطِّع يعتمد عليها.

10. حلقة التعلّم

هذا ما يجعله وكيلًا يتحسّن، لا مجرّد فهرس بحث جامد.

متى تسجّل درسًا

  1. حين تصحّح كود Flutter الذي كتبه Claude. سجّل ما كُتب وما كان يجب أن يُكتب والسبب.
  2. حين يرفض flutter analyze كودًا مولّدًا. سجّل الخطأ وإصلاحه.
  3. حين يجد flutter_check مخالفة ثم تُصلَح. مرّر رمز القاعدة بـ --rule ليظهر الدرس بجوارها.
  4. حين يتبيّن عُرف لا تغطّيه أي قاعدة. إن تكرّر، رقِّه إلى بطاقة في rules/.
